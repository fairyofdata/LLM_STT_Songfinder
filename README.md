# Songfinder : URFIT 팀 프로젝트의 음성·음악 매칭 모듈 (리팩토링 버전)

> 🏆 **한국무역협회 제47기 SCIT Master 프로젝트 발표회 우수상 (2위)** — 6인 팀 프로젝트 URFIT으로 수상  
> 👤 이 레포는 URFIT 중 백지헌이 혼자 맡은 음성 인식·검색·추천·Spotify 연동 모듈이며, 2026년 리팩토링도 혼자 진행했습니다.  
> ⚠️ **알림**: 본 레포지토리는 기존 [Huggingface Space](https://huggingface.co/spaces/fairyofdata/JPOP_STT_Module/tree/main)에서 구동되던 프로토타입을 **모던 웹 애플리케이션 아키텍처(Angular + FastAPI)** 로 완벽히 분리 및 리팩토링한 버전입니다. 이제 로컬 환경은 물론 Firebase, Cloud Run 등 다양한 클라우드 환경에 유연하게 배포할 수 있습니다.

![URFIT UI Preview](./Sample.png)

URFIT은 "음성인식 기반 AI 플레이리스트 생성 커뮤니티"로, 머릿속에 맴도는 희미한 가사나 흥얼거리는 멜로디만으로도 원하는 J-POP을 찾아주는 서비스입니다. 기존 노래 검색 서비스의 한계인 '부정확한 가사로는 검색 불가'와 '단순 검색 이후의 확장성 부족'을 해결하기 위해 기획되었습니다. UR-FIT은 아래를 중의적으로 함축하여 모두 프로젝트의 목적과 정체성을 담아 지어진 프로젝트명입니다. 
>  * 한국어: 얼핏 듣다 (얼핏 들은 노래를 찾아주고, 해당 노래를 듣고 공유할 수 있는 플랫폼)
>  * 영어: Your(UR) Fit (Music Recognition & Recommendation)
>  * 일본어: 運命のリズム、触れ合う意味の繋がり。

## 🎵 주요 기능

  * **‘대충 아는 가사’로 ‘그 노래’ 찾기**: 사용자가 흥얼거리거나 불분명한 가사를 입력해도 노래를 찾아줍니다.
  * **AI 기반 유사 곡 추천**: 검색된 곡의 가사, 분위기, 장르 등을 복합적으로 분석하여 사용자 취향에 맞는 유사한 곡 3개를 추천합니다.
  * **Spotify 플레이리스트 생성**: 추천받은 곡들을 한 번에 모아 Spotify 플레이리스트로 만들 수 있습니다.
  * **AI 플레이리스트 타이틀/설명 생성**: OpenAI의 GPT 모델이 추천 곡들의 특징을 분석해 창의적인 플레이리스트 제목과 설명을 자동으로 생성합니다.
  * **커뮤니티 기능**: 검색한 곡과 플레이리스트를 다른 사용자와 공유하고 소통할 수 있는 커뮤니티 기능을 제공합니다.

## 📊 평가: 곡 식별 성능

> 색인된 가사에서 만든 **합성 질의**로 잰 값입니다. 실제 사용자 질의나 실사용 정확도가 아닙니다. 재는 것은 「가사를 입력했을 때, 또는 TTS로 읽은 가사를 음성 경로에 넣었을 때 원래 곡을 찾는가」뿐이며, 사람의 실제 녹음, 콧노래·멜로디 검색은 평가하지 않았습니다.

![Recall by query type](./eval/results/recall_by_query_type.png)

자세한 기록: [연구개발 기록](docs/RESEARCH_LOG.md) · [결정 기록(ADR)](docs/adr/README.md) · [이어서 할 일](docs/NEXT_STEPS.md) · [포트폴리오용 요약](docs/PORTFOLIO.md)

### 방법
- **정답 단위는 곡**(`original_song_index`)입니다. 가사 줄 FAISS 검색 결과(top-2048줄)를 곡으로 묶어 중복을 없앤 순위로 Recall@1/5/10과 MRR을 셉니다.
- **질의 생성**: 가사 줄이 있는 450곡마다 공백 제외 8자 이상인 줄을 2개씩 무작위로 뽑고(전체 줄의 81.6%가 해당), 줄마다 아래 다섯 유형을 만듭니다. 시드당 4,488개, 시드 5개(0~4)이므로 질의는 모두 22,440개입니다.

  | 유형 | 만드는 법 |
  |---|---|
  | 원문 줄 | 색인된 줄 그대로 (검색이 제대로 도는지 보는 확인용) |
  | 앞 절반 | 글자 수 기준 앞 절반 |
  | 단어 30% 누락 | 단어 단위의 30% 삭제 (공백 토큰이 3개 이상이면 공백 기준, 아니면 문자 체계 경계 — 일본어 줄 대부분이 띄어쓰기가 없기 때문) |
  | 글자 오타 | 공백 제외 글자의 약 10%에 삽입·삭제·치환 (같은 문자 체계 안에서) |
  | 인접 두 줄 | 한 줄의 뒤 절반 + 같은 곡 다음 줄의 앞 절반 |

- **모호한 질의**: 원본 줄이나 질의 문자열이 (정규화 후) 다른 곡의 줄과 같으면, 즉 후렴·흔한 구절이면 따로 표시해 집계에서 나눕니다(시드당 87~109개, 대부분 「인접 두 줄」 유형).
- **앱 경로 재현**: `eval/common.py`가 `app.py`의 곡 식별 로직을 그대로 다시 구현합니다. `eval/check_against_app.py`로 `app.py` 함수를 직접 호출해 대조했고, 표본 140개(유형별 10개 + 음의 대조군 90개)에서 텍스트·음성 경로 모두 140/140 일치했습니다.
- **불확실성**: 시드 간 표준편차는 「같은 곡들 안에서 어느 줄을 뽑느냐」의 변동입니다. 그래서 곡을 다시 뽑는 부트스트랩(2,000회) 95% 신뢰구간을 함께 냅니다(전체 Recall@1 59.8–61.5%). 같은 질의를 짝지은 비교에는 McNemar 정확 검정을 씁니다.
- **음의 대조군**: DB에 없는 일상 문장 90개(한국어·영어·일본어 각 20, 중국어·유럽어·잡음 문자열 각 10, `eval/negatives.py`)입니다. 텍스트 경로가 「못 찾음」을 내는지 봅니다.

|---|---:|---:|---:|---:|---:|

| 글자 오타 ~10% | 890–894 | 79.8 ± 0.9 | 87.2 ± 0.3 | 89.8 ± 0.6 | 83.3 ± 0.5 |

- **음성 경로 로직**(전사 뒤 가사 줄 top-1, 판정선 없음)에 타이핑한 질의를 넣으면 곧 Recall@1입니다(전체 60.6%). 실제 음성(TTS)을 거친 결과는 아래 절에 있습니다.
- **텍스트 경로**(판정선 0.4)는 양성 질의의 100.0%를 통과시키고, 식별 정확도는 60.6 ± 0.6%로 Recall@1과 같습니다.
- **음의 대조군 오판정률은 0.4에서 93.3%**(84/90)입니다. 한국어·일본어·중국어·유럽어 문장은 모두, 영어는 85%, 잡음 문자열은 70%가 어떤 곡으로 「찾아집니다」. 짧은 가사 줄 22,806개 중 하나와는 다국어 임베딩 코사인이 쉽게 0.4를 넘기 때문입니다(대조군의 가사 top-1 점수 중앙값 0.60, 맞힌 양성 질의는 0.97).

### 음성 경로: TTS → whisper-1 (1,341개)

447곡에서 줄을 하나씩(시드 0의 첫 번째 원본 줄, 모호한 줄은 제외) 골라 「원문 줄」, 「앞 절반」, 「단어 30% 누락」 세 형태를 OpenAI `tts-1`(voice `alloy`)로 읽고 `whisper-1`로 전사한 뒤, 앱과 같은 음성 경로(가사 줄 top-1)로 곡을 찾았습니다. 같은 질의를 타이핑했을 때와 짝지어 비교합니다. 실행 비용은 약 $0.50입니다.

| 질의 유형 | n | 타이핑 정확도 | 음성 정확도 (95% CI) | 음성 Recall@10 | 전사 CER 중앙값 |
|---|---:|---:|---:|---:|---:|
| 원문 줄 | 447 | 100.0 | 75.6 (71.4–79.4) | 83.7 | 0.17 |
| 앞 절반 | 447 | 33.8 | 15.9 (12.8–19.6) | 34.9 | 0.27 |
| 단어 30% 누락 | 447 | 54.4 | 30.6 (26.6–35.1) | 42.5 | 0.29 |
| **전체** | 1,341 | **62.7** | **40.7 (38.1–43.4)** | **53.7** | 0.23 |

- STT를 거치면 같은 질의에서 정확도가 22.0%p 떨어집니다(타이핑으로는 맞혔는데 음성으로 틀린 경우 311개, 반대 16개). 원문 그대로 읽어도 4곡 중 1곡은 놓칩니다.
- CER에는 한자·가나 표기 차이와 문장부호 차이도 오류로 들어가므로, 실제 인식 오류보다 높게 나옵니다.
- TTS 클립의 99.6%가 5초 미만입니다(중앙값 1.5초). 앱의 `/stt`는 5초 미만 녹음을 거부하므로, 이 평가는 그 길이 제한을 건너뛴 파이프라인 성능입니다. 앱이 실제로 받는 길이로 다시 잰 결과는 다음 절에 있습니다.

### 음성 경로 본 실험: 로컬 TTS·Whisper, 앱 길이 질의 (449곡)

![Voice path by condition](./eval/results/audio_local.png)

한 곡당 질의 하나를 만들었습니다. 연속된 가사 2~6줄을 이어 붙여 말소리 중앙값 9.9초로 맞췄고, 5초 미만인 5.9%는 녹음처럼 뒤에 무음을 붙였습니다. 이 질의를 다섯 조건으로 읽혔습니다.

| 조건 | 기억 | 화자 |
|---|---|---|
| A | 정확 | 일본어 원어민 TTS (Kokoro 5, Supertonic 10, Windows 3 목소리) |
| B | 정확 | 한국인 발음: 일본어를 한글 독음으로 바꿔 한국어 TTS로 읽음 (Supertonic 10, Windows 1 목소리, 곡마다 표기 방식·속도·음높이를 바꿈) |
| C | 흐릿함 (아래 「섞기」 교란 40%) | 일본어 원어민 |
| D | 흐릿함 | 한국인 발음 |
| S | 한 줄만 | 일본어 원어민 |

TTS·전사 도구는 이번에 함께 만든 로컬 음성 서버 LocalTTS(별도 저장소, 아직 비공개)를 썼습니다. 클립마다 다음을 조합했습니다.
- 음질: 깨끗한 음성 / 「전화 대역 + 잔향 + 잡음(SNR 10~20dB)」
- Whisper large-v3의 언어 설정: 자동 감지(앱과 같음) / 일본어 고정

받아쓰기는 모두 8,996번입니다. 가사가 줄로 나뉘지 않은 곡 1곡(아래 「데이터 품질」)은 뺐습니다.

| 조건 (깨끗한 음질) | 타이핑 | 음성, 언어 자동 (앱) | 음성, 일본어 고정 |
|---|---:|---:|---:|
| A 정확 · 원어민 | 67.0 | 47.2 (42.5–51.9) | 45.9 |
| B 정확 · 한국인 발음 | 67.0 | **35.6** (31.2–40.1) | **43.2** |
| C 흐릿함 · 원어민 | 47.9 | 30.1 | 29.2 |
| D 흐릿함 · 한국인 발음 | 47.9 | 19.2 | 26.1 |
| S 한 줄만 · 원어민 | 99.6 | **76.2** (72.4–80.0) | 74.2 |

(곡을 1순위로 찾은 비율 %, 괄호는 곡 단위 부트스트랩 95% CI)

같은 곡끼리 짝지은 McNemar 검정으로 확인한 내용은 다음과 같습니다.
- **한국인 발음이면 Whisper가 한국어로 판단합니다.**
  - 언어 자동일 때 B 클립의 35%(155/449)를 한국어로 감지해 한글로 받아 적었습니다. 그래서 원어민보다 11.6%p 낮습니다(95 대 43, p = 1×10⁻⁵).
  - 일본어로 고정하면 원어민과의 차이가 사라집니다(45.9 vs 43.2, p = 0.32).
  - 다만 원어민 음성까지 일본어로 고정하면 영어 가사 줄을 가타카나로 받아 적어 오히려 소폭 떨어집니다(47.2 → 45.9, p = 0.03).
- **길게 말할수록 못 찾습니다.**
  - 한 줄만 말하면 76.2%, 5줄을 말하면 47.2%입니다(165 대 35, p = 2×10⁻²¹). 타이핑해도 99.6% 대 67.0%입니다.
  - 색인은 가사 한 줄 단위인데 질의는 여러 줄이라, 여러 줄을 섞은 임베딩이 다른 곡의 한 줄에 더 가까워지기 때문입니다.
  - 앱의 「5~15초 녹음」 안내와 줄 단위 색인이 서로 부딪히는 셈입니다.
- **열화 음질**에서는 원어민 47.2 → 42.5%(p = 0.02), 한 줄 76.2 → 67.9%로 떨어집니다.
  - 한국인 발음은 오히려 35.6 → 43.7%로 오릅니다. 잡음이 섞이면 Whisper가 한국어로 감지하는 비율이 35% → 9%로 줄기 때문입니다.
  - 언어 감지가 그만큼 불안정하다는 뜻이기도 합니다.
- **교차 확인:** 엔진이 전혀 다른 앞 절(OpenAI TTS → `whisper-1`, 원문 한 줄)의 75.6%와, 이번 한 줄 조건(로컬 TTS → Whisper large-v3)의 76.2%가 거의 같습니다.

### 음성 경로 개선안 추정 (앱은 수정하지 않음)

![Voice path before and after two fixes](./eval/results/voice_fixes.png)

이미 받아 적은 결과로 두 가지 수정의 효과를 추정했습니다(`eval/audio_fixes.py`).

1. **한국어 감지 시 일본어로 재전사:** 언어 자동으로 받아 적고, 한국어로 감지된 경우에만 `language="ja"`로 한 번 더 받아 적습니다.
   - 원어민 결과는 하나도 바뀌지 않습니다(추가 전사 0.4%).
   - B는 35.6 → 45.2%(49 대 6, p = 2×10⁻⁹)입니다.
2. **줄 단위 조각 투표:** 전사문을 가사 한 줄 길이(14자) 조각으로 나눠 각각 검색합니다. 조각별 1순위 점수와, 전사문 전체의 1순위(조각 수의 제곱근만큼 가중)를 곡별로 합쳐 투표합니다.
   - 조각만 쓰면 한 줄 질의가 손해를 보므로(76.2 → 66.6%) 전체 전사문 표를 함께 넣었습니다.
   - 가중치는 0.5/1/2 중 같은 데이터에서 골랐습니다. 그래서 다른 시드의 시작 줄로 만든 여러 줄 타이핑 질의(각 449개)로 따로 확인했고, 61.0 → 91.3%, 65.3 → 94.7%로 같은 효과가 났습니다.

| C 흐릿함 · 원어민 | 30.1 | 41.9 | 56 대 3 |
| D 흐릿함 · 한국인 발음 | 19.2 | 34.7 | 76 대 6 |
| S 한 줄만 | 76.2 | 75.7 | 1 대 3 (차이 없음) |

열화 음질에서도 같은 방향입니다(A 42.5 → 67.9, B 43.7 → 69.7).

### 흐릿한 기억: 어떤 오류에 약한가

![Recall@1 by kind of memory error](./eval/results/noise_curves.png)

원문 줄을 문절(내용어 + 뒤따르는 조사·조동사) 단위로 바꾼 교란 7종을, 문절의 20/40/60%에 적용했습니다(`eval/perturb.py`).

| 유형 | 방법 |
|---|---|
| 동의어 | 일본어 WordNet 동의어 중 가사 DB에 있는 말을, 마스크 언어 모델(XLM-R)로 문맥에 맞는 것을 골라 바꿈 |
| 소리 비슷한 말 | 가나 읽기가 한 모라만 다른 같은 품사 단어로 바꿈 (몬더그린) |
| 조사 바꾸기·빼기 | は/が, に/へ/で 등 같은 종류 안에서 바꾸거나 뺌 |
| 어절 빼기 | 문절을 통째로 뺌 |
| 문맥상 그럴듯한 말 | ELECTRA 방식. 마스크 언어 모델이 같은 문자 체계·품사·활용의 다른 말로 채움 |
| 같은 읽기 다른 표기 | 한자 단어를 같은 읽기의 다른 표기나 가나로 바꿈 |
| 섞기 | 앞의 넷을 무작위로 섞음 |

유형마다 적용할 수 있는 줄이 다르므로, 모든 유형이 적용되는 같은 원본 줄 1,607개(시드 3개)로 비교했습니다. 원래 시드 5개로 설계했지만, 세 시드의 결과가 서로 거의 같아 계산 시간을 줄이려고 3개에서 멈췄습니다.

| 유형 | 20% | 40% | 60% |
|---|---:|---:|---:|
| 조사 바꾸기·빼기 | 97.4 | 94.4 | 93.2 |
| 동의어 | 82.5 | 72.5 | 66.1 |
| 섞기 | 77.7 | 54.5 | 35.1 |
| 어절 빼기 | 69.0 | 38.1 | 14.6 |
| 소리 비슷한 말 | 68.2 | 44.2 | 26.6 |
| 같은 읽기 다른 표기 | 65.3 | 40.6 | 22.7 |
| 문맥상 그럴듯한 말 | 63.7 | 40.3 | 24.1 |

(Recall@1 %, 95% CI 폭 ±2~3%p)

다국어 의미 임베딩이라 **뜻이 유지되면 버티지만, 소리나 표기가 같은 다른 말에는 약합니다.** 그런데 음성 입력(STT의 한자 선택)과 비원어민 발음에서 생기는 오류는 대부분 이쪽입니다. 그래서 가나 읽기 기반 색인을 보조로 두는 것이 다음 개선 후보입니다.

교란이 「사람이 실제로 이렇게 잘못 기억할 법한가」는 표본 100개를 사람이 맹검으로 판정해 확인할 예정입니다(`eval/review_sheet.py`; 시트는 가사를 담고 있어 레포 밖에 둡니다). 판정 전까지 이 곡선은 「기억 오류 흉내」가 아니라 「교란 강건성」으로만 읽어야 합니다.

### 판정선 바꾸기 (0.30~0.90)

![Threshold trade-off](./eval/results/threshold_tradeoff.png)

| 판정선 | 양성 통과율 | 양성 식별 정확도 | 음의 대조군 오판정률 |
|---:|---:|---:|---:|
| 0.40 (현재) | 100.0 | 60.6 | 93.3 |
| 0.60 | 99.6 | 60.5 | 51.1 |
| 0.70 | 97.6 | 60.0 | 31.1 |
| 0.80 | 90.6 | 57.6 | 7.8 |
| 0.90 | 65.1 | 47.7 | 2.2 |

0.6까지 올려도 정확도는 거의 그대로이고, 0.8에서는 정확도 3.0%p를 내주고 오판정률이 93%에서 8%로 떨어집니다. 다만 대조군이 일상 문장 90개뿐이라 판정선을 정할 근거로는 부족합니다. 정확도와 함께 보여 주려는 값입니다.

### 의심 버그: 텍스트 경로의 요약 분기 (보고만 함, 앱은 수정하지 않음)
`search_pipeline_from_text`는 요약 검색이 이기면 `line_metadata[I_summary[0][0]]['original_song_index']`로 곡을 찾습니다. `I_summary`는 곡 인덱스(0~460)이므로 결과는 줄 메타데이터의 앞쪽 461줄이 속한 곡 0~6번, 7곡 중 하나로만 나옵니다. 「현행」과 「고친 변형(`I_summary[0][0]`을 그대로 곡 인덱스로 사용)」을 둘 다 평가했습니다.

| 질의 | 요약 분기가 이기는 비율 | 현행 정확도 | 고친 변형 정확도 |
|---|---:|---:|---:|
| 가사 기반 합성 질의 (위 22,440개) | 0.0% | 60.6% | 60.6% |
| 음의 대조군 90개 | 0.0% | — | — |
| 곡 요약문 전체를 질의로 (461개, 버그 탐침) | 100.0% | 0.2% (7곡만 반환) | 100.0% |
| 곡 요약문 앞 절반 (461개, 버그 탐침) | 75.7% | 1.1% | 37.1% |

가사 질의에서는 가사 top-1 점수가 늘 요약 점수보다 높아 버그가 드러나지 않습니다. 「요약과 비슷한 분위기 설명」처럼 요약 분기가 이기는 질의에서는 사실상 항상 엉뚱한 곡이 나옵니다. 탐침 질의는 DB의 요약문 자체라 실제 사용자 질의가 아니고, 버그의 영향 범위를 보여 주는 용도입니다.

### 데이터 품질: 이상치 줄 (`eval/data_quality.py`, 데이터 파일은 수정하지 않음)

| 이상치 | 색인 중 비율 | 오답 1순위 중 비율 | 판단 |
|---|---:|---:|---|
| 공백 제외 6자 이하 짧은 줄 | 7.9% | **25.0%** (정답 쪽은 0.65%) | 엉뚱한 질의를 끌어당기는 「허브」 |
| 문장부호만 있는 줄 | 5.2% | 0.06% | 무해 |
| 가사 전체가 한 줄로 붙은 곡 | 1곡 (620자 한 줄) | 0% | 임베딩 모델이 앞부분만 읽으므로, 이 곡은 가사 뒷부분으로 찾을 수 없음 |

짧은 줄과 문장부호 줄을 평가 쪽에서 색인에서 빼 보면, 시드 0 질의의 Recall@1이 60.5% → 61.8%로 오릅니다. 새로 맞은 질의가 70개, 새로 틀린 질의가 14개입니다(p = 4×10⁻¹⁰). 음의 대조군 오판정률은 변화가 없습니다. 다만 짧은 후렴구만 기억하는 사용자는 그 줄을 못 찾게 되므로, 삭제보다는 짧은 줄을 앞뒤 줄과 묶어 색인하는 쪽이 낫습니다.

### 한계
- **합성 질의**입니다. 실제 사용자가 가사를 잘못 기억하는 방식(다른 말로 바꾸기, 잘못 들은 발음, 로마자·한글 표기, 언어 섞기)은 반영하지 못했습니다. 위 수치를 실사용 정확도로 읽으면 안 됩니다.
- 「원문 줄」은 질의가 색인과 같으므로 100%가 당연한 확인용입니다.
- **후렴 중복**: 모호성은 정규화 후 완전히 같은 줄만으로 판정했습니다. 거의 같은 줄(한 글자 차이 등)은 「모호하지 않음」에 남아 있습니다. 공백 제외 8자 미만인 줄은 원본 줄로 쓰지 않았고, 가사 줄이 없는 11곡은 빠져 있습니다.
- **음성**: 사람의 녹음은 평가하지 않았습니다.
  - 음성은 모두 TTS입니다. OpenAI 1개 목소리로 1,341개, 로컬 29개 목소리로 2,249개입니다. 사람의 말투, 노래, 콧노래와는 다릅니다.
  - 음성 실험은 시드 0의 질의만 썼습니다.
  - 「한국인 발음」은 사전 읽기를 한글로 옮겨 한국어 TTS가 읽은 근사입니다. 실제 한국인 팬은 원곡 발음을 흉내 내므로 숙련도에 따라 다릅니다. 한자 읽기는 사전(UniDic) 기준이라 가사의 특수한 읽기와 다를 수 있습니다.
  - 잡음은 합성(분홍 잡음, 합성 잔향)입니다.
- **개선안 추정**은 이미 받아 적은 결과를 다시 검색한 것입니다. 실제 앱에 넣으면 추가 전사의 지연과 비용이 생깁니다. 조각 투표 가중치는 같은 데이터에서 골랐고, 다른 시드의 타이핑 질의로만 따로 확인했습니다.
- **교란 7종**은 사람의 기억 오류를 흉내 내도록 설계했지만, 그 타당성은 사람 판정(진행 전)으로만 확인할 수 있습니다.
- **음의 대조군**은 직접 쓴 일상 문장 90개입니다. DB에 없는 다른 J-POP 곡의 가사라면 오판정률은 더 높을 가능성이 큽니다.
- 비교 기준선(다른 임베딩 모델, BM25 등) 없이 현재 앱 구성 하나만 쟀습니다.

## 🚀 로컬 실행 방법 (How to Run)

프론트엔드와 백엔드 서버를 각각 실행해야 합니다.

### 사전 준비사항
1. Python 3.10+ 설치 (오류 시 `audioop-lts` 등 추가 확인)
2. Node.js (v18+) 및 npm 설치
3. [Spotify Developer Dashboard](https://developer.spotify.com/dashboard)에서 앱 생성 및 `Client ID`, `Client Secret` 획득
   * **Redirect URI** 설정 필수: `http://localhost:7860/callback` (주의: https가 아닌 http 사용)
4. `.env` 파일 (또는 환경변수) 설정: `OPENAI_API_KEY`, `SPOTIPY_CLIENT_ID`, `SPOTIPY_CLIENT_SECRET`, `SPOTIPY_REDIRECT_URI=http://localhost:7860/callback`

### 원클릭 실행 (Windows 전용)
바탕화면 등에 제공된 `Start_JPOP_Finder.bat` 파일을 더블클릭하면 프론트엔드와 백엔드가 동시에 실행됩니다. (최초 실행 시 AI 모델 다운로드로 인해 1~2분 소요될 수 있습니다.)

### 수동 실행
**1. Backend 서버 실행**
```bash
pip install -r requirements.txt
# 파이썬 3.13 이상 환경에서 오류 시: pip install audioop-lts
python app.py
```
* 서버가 `http://localhost:7860`에서 구동됩니다. (첫 실행 시 수백 MB 모델이 캐시 다운로드됩니다.)

**2. Frontend 서버 실행**
새 터미널을 열고 다음을 실행합니다.
```bash
cd frontend
npm install
npm start
```
* 서버가 `http://localhost:4200`에서 구동됩니다. 브라우저로 해당 주소에 접속하세요.
