# Songfinder : URFIT 팀 프로젝트의 음성·음악 매칭 모듈 (리팩토링 버전)

> 🏆 **한국무역협회 제47기 SCIT Master 프로젝트 발표회 우수상 (2위)** — 6인 팀 프로젝트 URFIT으로 수상  
> 👤 이 레포는 URFIT 중 백지헌이 혼자 맡은 음성 인식·검색·추천·Spotify 연동 모듈이며, 2026년 리팩토링도 혼자 진행했습니다.  
> ⚠️ **알림**: 본 레포지토리는 기존 [Huggingface Space](https://huggingface.co/spaces/fairyofdata/JPOP_STT_Module/tree/main)에서 구동되던 프로토타입을 **모던 웹 애플리케이션 아키텍처(Angular + FastAPI)** 로 완벽히 분리 및 리팩토링한 버전입니다. 이제 로컬 환경은 물론 Firebase, Cloud Run 등 다양한 클라우드 환경에 유연하게 배포할 수 있습니다.

![URFIT UI Preview](./Sample.png)

URFIT은 "음성인식 기반 AI 플레이리스트 생성 커뮤니티"로, 머릿속에 맴도는 희미한 가사나 흥얼거리는 멜로디만으로도 원하는 J-POP을 찾아주는 서비스입니다. 기존 노래 검색 서비스의 한계인 '부정확한 가사로는 검색 불가'와 '단순 검색 이후의 확장성 부족'을 해결하기 위해 기획되었습니다. UR-FIT은 아래를 중의적으로 함축하여 모두 프로젝트의 목적과 정체성을 담아 지어진 프로젝트명입니다. 
>  * 한국어: 얼핏 듣다 (얼핏 들은 노래를 찾아주고, 해당 노래를 듣고 공유할 수 있는 플랫폼)
>  * 영어: Your(UR) Fit (Music Recognition & Recommendation)
>  * 일본어: 運命のリズム、触れ合う意味の繋がり。

## 🎵 주요 기능

  * **‘대충 아는 가사’로 ‘그 노래’ 찾기**: 사용자가 흥얼거리거나 불분명한 가사를 입력해도 노래를 찾아줍니다.
  * **AI 기반 유사 곡 추천**: 검색된 곡의 가사, 분위기, 장르 등을 복합적으로 분석하여 사용자 취향에 맞는 유사한 곡 3개를 추천합니다.
  * **Spotify 플레이리스트 생성**: 추천받은 곡들을 한 번에 모아 Spotify 플레이리스트로 만들 수 있습니다.
  * **AI 플레이리스트 타이틀/설명 생성**: OpenAI의 GPT 모델이 추천 곡들의 특징을 분석해 창의적인 플레이리스트 제목과 설명을 자동으로 생성합니다.
  * **커뮤니티 기능**: 검색한 곡과 플레이리스트를 다른 사용자와 공유하고 소통할 수 있는 커뮤니티 기능을 제공합니다.

## 📊 평가: 곡 식별 성능

> 색인된 가사에서 만든 **합성 질의**로 잰 값입니다. 실제 사용자 질의나 실사용 정확도가 아닙니다. 재는 것은 「가사를 입력했을 때(또는 음성 경로에서 전사가 완벽할 때) 원래 곡을 찾는가」뿐이며, 콧노래·멜로디 검색은 평가하지 않았습니다.

![Recall by query type](./eval/results/recall_by_query_type.png)

### 방법
- **정답 단위는 곡**(`original_song_index`)입니다. 가사 줄 FAISS 검색 결과(top-2048줄)를 곡으로 묶어 중복을 없앤 순위로 Recall@1/5/10과 MRR을 셉니다.
- **질의 생성**: 가사 줄이 있는 450곡마다 공백 제외 8자 이상인 줄을 2개씩 무작위로 뽑고(전체 줄의 81.6%가 해당), 줄마다 아래 다섯 유형을 만듭니다. 시드당 4,488개, 시드 5개(0~4)이므로 질의는 모두 22,440개입니다.

  | 유형 | 만드는 법 |
  |---|---|
  | 원문 줄 | 색인된 줄 그대로 (검색이 제대로 도는지 보는 확인용) |
  | 앞 절반 | 글자 수 기준 앞 절반 |
  | 단어 30% 누락 | 단어 단위의 30% 삭제 (공백 토큰이 3개 이상이면 공백 기준, 아니면 문자 체계 경계 — 일본어 줄 대부분이 띄어쓰기가 없기 때문) |
  | 글자 오타 | 공백 제외 글자의 약 10%에 삽입·삭제·치환 (같은 문자 체계 안에서) |
  | 인접 두 줄 | 한 줄의 뒤 절반 + 같은 곡 다음 줄의 앞 절반 |

- **모호한 질의**: 원본 줄이나 질의 문자열이 (정규화 후) 다른 곡의 줄과 같으면, 즉 후렴·흔한 구절이면 따로 표시해 집계에서 나눕니다(시드당 87~109개, 대부분 「인접 두 줄」 유형).
- **앱 경로 재현**: `eval/common.py`가 `app.py`의 곡 식별 로직을 그대로 다시 구현합니다. `eval/check_against_app.py`로 `app.py` 함수를 직접 호출해 대조했고, 표본 140개(유형별 10개 + 음의 대조군 90개)에서 텍스트·음성 경로 모두 140/140 일치했습니다.
- **음의 대조군**: DB에 없는 일상 문장 90개(한국어·영어·일본어 각 20, 중국어·유럽어·잡음 문자열 각 10, `eval/negatives.py`)입니다. 텍스트 경로가 「못 찾음」을 내는지 봅니다.

### 결과 (모호한 질의 제외, 시드 5개 평균 ± 표준편차, %)

| 질의 유형 | 시드당 질의 수 | Recall@1 | Recall@5 | Recall@10 | MRR |
|---|---:|---:|---:|---:|---:|
| 원문 줄 (확인용) | 890–894 | 100.0 ± 0.0 | 100.0 ± 0.0 | 100.0 ± 0.0 | 100.0 ± 0.0 |
| 앞 절반 | 880–885 | 32.9 ± 1.0 | 50.8 ± 1.5 | 57.5 ± 1.8 | 41.5 ± 1.0 |
| 단어 30% 누락 | 886–892 | 53.3 ± 1.5 | 66.4 ± 1.5 | 71.1 ± 1.3 | 59.5 ± 1.5 |
| 글자 오타 ~10% | 890–894 | 79.8 ± 0.9 | 87.2 ± 0.3 | 89.8 ± 0.6 | 83.3 ± 0.5 |
| 인접 두 줄 | 828–837 | 35.3 ± 1.6 | 53.4 ± 1.5 | 61.6 ± 1.3 | 44.2 ± 1.4 |
| **전체** | 4,379–4,401 | **60.6 ± 0.6** | **71.8 ± 0.5** | **76.2 ± 0.5** | **66.0 ± 0.5** |
| 모호한 질의 (참고) | 87–109 | 20.5 ± 4.7 | 41.6 ± 5.3 | 53.0 ± 5.9 | 31.4 ± 4.1 |

- **음성 경로 로직**(전사 뒤 가사 줄 top-1, 판정선 없음)에 타이핑한 질의를 넣으면 곧 Recall@1입니다(전체 60.6%).
- **텍스트 경로**(판정선 0.4)는 양성 질의의 100.0%를 통과시키고, 식별 정확도는 60.6 ± 0.6%로 Recall@1과 같습니다.
- **음의 대조군 오판정률은 0.4에서 93.3%**(84/90)입니다. 한국어·일본어·중국어·유럽어 문장은 모두, 영어는 85%, 잡음 문자열은 70%가 어떤 곡으로 「찾아집니다」. 짧은 가사 줄 22,806개 중 하나와는 다국어 임베딩 코사인이 쉽게 0.4를 넘기 때문입니다(대조군의 가사 top-1 점수 중앙값 0.60, 맞힌 양성 질의는 0.97).

### 판정선 바꾸기 (0.30~0.90)

![Threshold trade-off](./eval/results/threshold_tradeoff.png)

| 판정선 | 양성 통과율 | 양성 식별 정확도 | 음의 대조군 오판정률 |
|---:|---:|---:|---:|
| 0.40 (현재) | 100.0 | 60.6 | 93.3 |
| 0.60 | 99.6 | 60.5 | 51.1 |
| 0.70 | 97.6 | 60.0 | 31.1 |
| 0.80 | 90.6 | 57.6 | 7.8 |
| 0.90 | 65.1 | 47.7 | 2.2 |

0.6까지 올려도 정확도는 거의 그대로이고, 0.8에서는 정확도 3.0%p를 내주고 오판정률이 93%에서 8%로 떨어집니다. 다만 대조군이 일상 문장 90개뿐이라 판정선을 정할 근거로는 부족합니다. 정확도와 함께 보여 주려는 값입니다.

### 의심 버그: 텍스트 경로의 요약 분기 (보고만 함, 앱은 수정하지 않음)
`search_pipeline_from_text`는 요약 검색이 이기면 `line_metadata[I_summary[0][0]]['original_song_index']`로 곡을 찾습니다. `I_summary`는 곡 인덱스(0~460)이므로 결과는 줄 메타데이터의 앞쪽 461줄이 속한 곡 0~6번, 7곡 중 하나로만 나옵니다. 「현행」과 「고친 변형(`I_summary[0][0]`을 그대로 곡 인덱스로 사용)」을 둘 다 평가했습니다.

| 질의 | 요약 분기가 이기는 비율 | 현행 정확도 | 고친 변형 정확도 |
|---|---:|---:|---:|
| 가사 기반 합성 질의 (위 22,440개) | 0.0% | 60.6% | 60.6% |
| 음의 대조군 90개 | 0.0% | — | — |
| 곡 요약문 전체를 질의로 (461개, 버그 탐침) | 100.0% | 0.2% (7곡만 반환) | 100.0% |
| 곡 요약문 앞 절반 (461개, 버그 탐침) | 75.7% | 1.1% | 37.1% |

가사 질의에서는 가사 top-1 점수가 늘 요약 점수보다 높아 버그가 드러나지 않습니다. 「요약과 비슷한 분위기 설명」처럼 요약 분기가 이기는 질의에서는 사실상 항상 엉뚱한 곡이 나옵니다. 탐침 질의는 DB의 요약문 자체라 실제 사용자 질의가 아니고, 버그의 영향 범위를 보여 주는 용도입니다.

### 한계
- **합성 질의**입니다. 실제 사용자가 가사를 잘못 기억하는 방식(다른 말로 바꾸기, 잘못 들은 발음, 로마자·한글 표기, 언어 섞기)은 반영하지 못했습니다. 위 수치를 실사용 정확도로 읽으면 안 됩니다.
- 「원문 줄」은 질의가 색인과 같으므로 100%가 당연한 확인용입니다.
- **후렴 중복**: 모호성은 정규화 후 완전히 같은 줄만으로 판정했습니다. 거의 같은 줄(한 글자 차이 등)은 「모호하지 않음」에 남아 있습니다. 공백 제외 8자 미만인 줄은 원본 줄로 쓰지 않았고, 가사 줄이 없는 11곡은 빠져 있습니다.
- **음성**: 실제 녹음은 평가하지 않았습니다. TTS → `whisper-1` 소량 평가 스크립트(`eval/audio_eval.py`, 50개, 예상 비용 약 $0.03)는 있지만 이 환경에 OpenAI 키가 없어 실행하지 않았습니다. 실행하더라도 TTS 낭독일 뿐 사람의 말·노래·콧노래가 아닙니다.
- **음의 대조군**은 직접 쓴 일상 문장 90개입니다. DB에 없는 다른 J-POP 곡의 가사라면 오판정률은 더 높을 가능성이 큽니다.
- 비교 기준선(다른 임베딩 모델, BM25 등) 없이 현재 앱 구성 하나만 쟀습니다.

### 재현
레포 루트에서 (Windows, Python 3.14 기준. `venv/`는 gitignore 대상):

```bash
py -3 -m venv venv && venv\Scripts\python -m pip install torch --index-url https://download.pytorch.org/whl/cpu && venv\Scripts\python -m pip install -r eval/requirements.txt && venv\Scripts\python eval/run_eval.py && venv\Scripts\python eval/plot.py
```

- 결과: `eval/results/seed_<n>.json`(질의별 원자료: id·곡 인덱스·원본 줄 인덱스·점수·예측, 가사 문장 없음), `summary.json`(평균 ± 표준편차, 판정선 스윕, 대조군, 버그 탐침), `negatives.json`, `summary_probe.json`
- `app.py` 대조: `venv\Scripts\python -m pip install -r requirements.txt audioop-lts` 후 `venv\Scripts\python eval/check_against_app.py`
- 음성 소량 평가: `venv\Scripts\python eval/audio_eval.py`(비용 추정만), `--run`(실행, `.env`나 환경변수의 `openai`/`OPENAI_API_KEY` 사용)
- 사용 버전: faiss-cpu 1.15.1, sentence-transformers 6.1.0, torch 2.14.1+cpu, numpy 2.5.4, matplotlib 3.11.2

## 🛠 아키텍처 및 기술 스택 (리팩토링 적용)

기존 단일 애플리케이션 구조에서 확장성과 유지보수성을 위해 프론트엔드와 백엔드를 완벽히 분리했습니다.

### 1. Frontend (Angular)
  * **Framework**: Angular 17+ (기존 Vanilla JS/HTML 기반 코드 포팅)
  * **Styling**: TailwindCSS, SCSS
  * **주요 기능**: Spotify Web Playback SDK 연동, 마이크 오디오 스트림(MediaRecorder) 캡처 및 전송

### 2. Backend (FastAPI)
  * **Framework**: FastAPI (Python 3.10+)
  * **AI/ML**:
      * OpenAI **Whisper** (STT 변환)
      * **SentenceTransformer** (`paraphrase-multilingual-MiniLM-L12-v2`) 및 **FAISS** (가사 벡터 유사도 검색)
      * OpenAI **GPT-3.5-turbo** (플레이리스트 제목 및 설명 자동 생성)
  * **주요 기능**: Spotify OAuth 인증, STT 분석, 벡터 검색 API 제공, CORS 완벽 지원

## 🚀 로컬 실행 방법 (How to Run)

프론트엔드와 백엔드 서버를 각각 실행해야 합니다.

### 사전 준비사항
1. Python 3.10+ 설치 (오류 시 `audioop-lts` 등 추가 확인)
2. Node.js (v18+) 및 npm 설치
3. [Spotify Developer Dashboard](https://developer.spotify.com/dashboard)에서 앱 생성 및 `Client ID`, `Client Secret` 획득
   * **Redirect URI** 설정 필수: `http://localhost:7860/callback` (주의: https가 아닌 http 사용)
4. `.env` 파일 (또는 환경변수) 설정: `OPENAI_API_KEY`, `SPOTIPY_CLIENT_ID`, `SPOTIPY_CLIENT_SECRET`, `SPOTIPY_REDIRECT_URI=http://localhost:7860/callback`

### 원클릭 실행 (Windows 전용)
바탕화면 등에 제공된 `Start_JPOP_Finder.bat` 파일을 더블클릭하면 프론트엔드와 백엔드가 동시에 실행됩니다. (최초 실행 시 AI 모델 다운로드로 인해 1~2분 소요될 수 있습니다.)

### 수동 실행
**1. Backend 서버 실행**
```bash
pip install -r requirements.txt
# 파이썬 3.13 이상 환경에서 오류 시: pip install audioop-lts
python app.py
```
* 서버가 `http://localhost:7860`에서 구동됩니다. (첫 실행 시 수백 MB 모델이 캐시 다운로드됩니다.)

**2. Frontend 서버 실행**
새 터미널을 열고 다음을 실행합니다.
```bash
cd frontend
npm install
npm start
```
* 서버가 `http://localhost:4200`에서 구동됩니다. 브라우저로 해당 주소에 접속하세요.

## 🖼️ 사용 가이드

1. **검색 시작**: 메인 화면에서 **음성으로 찾기** 또는 **텍스트로 찾기** 버튼을 클릭합니다.
2. **STT 검색**: 마이크 권한을 허용하고 5~15초간 콧노래를 흥얼거리거나 가사를 말해보세요.
3. **결과 확인 및 재생**: FAISS 기반 검색 결과와 유사 곡들이 출력됩니다. Spotify 연동 후 Web Player로 바로 감상 가능합니다.
4. **플레이리스트 생성**: "이 곡들로 플레이리스트 만들기"를 누르면 AI가 제목/설명을 생성하여 내 Spotify 계정에 직접 저장해줍니다.

## 💡 프로젝트의 가치 및 향후 계획

  * **AI 기술의 실용적 응용**: 사용자의 불편함을 해결하는 실용적인 서비스에 최신 AI 기술을 응용했습니다.
  * **확장 가능한 서비스 설계**: 마이크로서비스 아키텍처(분리형 구조)를 통해 향후 기능 확장이 용이하도록 설계했습니다.
  * **향후 계획**: 
    - 청취 기록 기반의 개인화 추천 기능 도입
    - Firebase Hosting (Frontend) + Cloud Run (Backend) 클라우드 배포 완전 자동화
    - 모바일 앱 버전 (Ionic / React Native) 출시를 통한 접근성 강화
