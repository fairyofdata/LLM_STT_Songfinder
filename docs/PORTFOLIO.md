## 정말 찾아 주는가: 숫자로 확인했습니다

데모가 잘 돌아가는 것과 「흐릿한 기억으로도 찾는가」는 다른 문제입니다. 그래서 **곡 식별 단계만 떼어 정량 평가**했습니다. 추천 품질과 UI는 이 평가의 범위가 아닙니다.

![평가 설계](assets/eval_design.png)

- **질의:** 색인된 가사로 합성 질의를 만들었습니다(실제 사용자 질의가 아님). 원문, 앞 절반, 오타, 단어 누락, 두 줄 이어 붙이기의 5가지와, 기억 오류 7종을 20/40/60% 강도로 적용한 것이 있습니다.
- **음성:** 직접 만든 로컬 TTS(일본어 목소리 18개, 한국어 11개)로 읽고 Whisper로 전사했습니다. 한국인 화자를 흉내 내려고 일본어를 한글 독음으로 바꿔 한국어 목소리로 읽힌 조건과, 전화 음질·잔향·잡음 조건도 넣었습니다.
- **앱 로직 재현:** 판정 로직을 그대로 재구현하고, 실제 `app.py` 함수와 표본 140개에서 140/140 일치를 확인했습니다.
- **통계:** 곡 단위 부트스트랩 95% 신뢰구간, 짝지은 비교에는 McNemar 검정을 썼습니다.
- **저작권:** 가사 원문은 결과·차트·로그 어디에도 남기지 않았습니다. 질의는 id로만 기록했습니다.

### 핵심 결과

**1. 입력한 가사 (질의 21,953개, 시드 5개)**

![질의 유형별 Recall](../eval/results/recall_by_query_type.png)

| 질의 유형 | Recall@1 | Recall@10 |
|---|---:|---:|
| 오타 약 10% | 79.8% | 89.8% |
| 단어 30% 누락 | 53.3% | 71.1% |
| 인접 두 줄 일부 | 35.3% | 61.6% |
| 앞 절반만 | 32.9% | 57.5% |
| **전체** (원문 줄 포함) | **60.6%** (95% CI 59.8–61.5) | **76.2%** |

**2. 어떤 기억 오류에 약한가 (공통 질의 1,607개, 시드 3개)**

![기억 오류 유형별 Recall@1](../eval/results/noise_curves.png)

**뜻에는 강하고 소리에는 약합니다.** 바꾼 어절 비율이 20%에서 60%로 늘 때 Recall@1은 다음과 같이 변했습니다.
- 조사를 바꾸거나 빼도 거의 그대로입니다(97% → 93%).
- 동의어로 바꾸면 꽤 버팁니다(83% → 66%).
- 소리가 비슷한 말(68% → 27%)과 같은 읽기의 다른 한자(65% → 23%)에서는 크게 무너집니다.

의미 임베딩이라 발음 정보를 쓰지 않기 때문입니다. 그런데 음성 입력과 비원어민 발음에서 생기는 오류는 대부분 「소리」 쪽입니다.

**3. 말한 가사**
- **OpenAI TTS → `whisper-1` (앱과 같은 STT, 1,341개):** 같은 질의를 입력하면 62.7%인데, 음성으로는 40.7%입니다. 짝지은 비교에서 입력으로만 맞힌 경우가 311개, 음성으로만 맞힌 경우가 16개입니다.
- **로컬 TTS·Whisper, 앱이 실제로 받는 길이의 질의(말소리 중앙값 10초, 449곡):** 받아쓰기 8,996번으로 조건을 비교했습니다.

![조건별 음성 경로 정확도](../eval/results/audio_local.png)

| 조건 (깨끗한 음질, 앱 설정) | 입력 | 음성 |
|---|---:|---:|
| 가사 2~6줄, 일본어 원어민 | 67.0% | 47.2% |
| 가사 2~6줄, **한국인 발음** | 67.0% | **35.6%** |
| 가사 한 줄만, 일본어 원어민 | 99.6% | 76.2% |

- **한국인 발음:** Whisper가 35%를 「한국어」로 판단해 한글로 받아 적어서 정확도가 떨어집니다.
- **여러 줄을 말할 때:** 한 줄일 때보다 오히려 못 찾습니다(76% → 47%). 가사를 한 줄씩 색인했기 때문입니다.
- **교차 확인:** 엔진이 다른 OpenAI TTS → `whisper-1`의 한 줄 결과(75.6%)와 거의 같습니다.

## 평가로 찾은 것과 개선 방향

| 발견 | 근거 | 개선 방향 |
|---|---|---|
| 「못 찾음」 판정선(0.4)이 거의 아무것도 거르지 못함 | DB에 없는 문장 90개 중 93.3%가 어떤 곡으로 「찾아짐」 | 0.8로 올리면 오판정률 7.8%, 정확도 손실 3.0%p. 대조군을 늘려 다시 정할 것 |
| 텍스트 검색의 요약 분기 인덱스 버그 | 요약 분기로 가는 질의에서 현행 0.2%(곡 0~6번만 반환), 고친 변형 100% | 한 줄 수정. 가사 질의에서는 발동하지 않아 지금까지 드러나지 않았음 |
| 의미 검색이 소리 오류에 약함 | 위 2번 결과 | 가나 읽기(발음) 기반 색인을 보조로 추가 |
| 한국인 발음을 Whisper가 한국어로 받아 적음 | 한국인 발음 클립의 35%. 원어민보다 11.6%p 낮음 (p = 1×10⁻⁵) | 한국어로 감지될 때만 일본어로 재전사. 원어민 결과는 그대로, 한국인 발음 35.6 → 45.2% |
| 여러 줄 음성과 줄 단위 색인이 맞지 않음 | 한 줄 76%, 5줄 47% (p = 2×10⁻²¹) | 전사문을 줄 길이로 잘라 검색 후 투표. 5줄 47 → 74%, 한 줄은 그대로 |
| 짧은 가사 줄이 오답을 끌어당김 | 색인의 7.9%인데 오답 1순위의 25% | 짧은 줄은 앞뒤 줄과 묶어 색인 (빼면 Recall@1 +1.3%p, p = 4×10⁻¹⁰) |
| 가사가 줄로 나뉘지 않은 곡 | 1곡이 620자 한 줄 | 데이터 정제 단계에서 줄 나누기 |

**두 음성 수정을 함께 적용한 추정치:** 같은 음성, 같은 전사문으로 계산했습니다.

![현재 vs 두 수정 적용](../eval/results/voice_fixes.png)

| 조건 | 앱 현재 | 두 수정 적용 |
|---|---:|---:|
| 한국인 발음, 2~6줄 | 35.6% | **69.3%** (새로 맞음 156 대 새로 틀림 5) |
| 원어민, 2~6줄 | 47.2% | **74.4%** (123 대 1) |
| 원어민, 한 줄 | 76.2% | 75.7% (차이 없음) |

조각 투표의 가중치는 같은 데이터에서 골랐습니다. 그래서 다른 시드로 만든 여러 줄 입력 질의로 따로 확인했고, 61 → 91%, 65 → 95%로 효과가 재현됐습니다.

## 방법론에서 신경 쓴 점

- **재는 대상을 앱과 일치시켰습니다.** 평가용으로 로직을 새로 쓰면 앱과 어긋날 수 있어서, 원본 함수와 결과를 대조했습니다.
- **좋게 나오는 숫자보다 해석 범위를 먼저 정했습니다.**
  - 「원문 그대로 100%」는 당연한 확인용이라 성과로 내세우지 않았습니다.
  - TTS 음성은 「낙관적 상한」으로만 해석합니다.
  - 합성 질의라서 실사용 정확도라고 부르지 않습니다.
- **모호한 정답을 따로 셌습니다.** 후렴처럼 여러 곡에 있는 줄은 정답이 모호하므로 분리해 집계했습니다.
- **교란이 실제 기억 오류를 닮았는지 사람이 맹검으로 판정합니다.** 표본 100개이고, *(판정 후 채움)*.
- **평가 도중 방법을 고쳤습니다.**
  - 처음엔 1~2초짜리 한 줄 음성이었는데, 앱이 5초 미만을 거부한다는 걸 보고 앱이 실제로 받는 길이로 바꿨습니다.
  - 기억 오류 교란은 형태소가 아닌 문절 단위로, 같은 문자 체계 안에서만 바꾸도록 수정했습니다.

## 함께 만든 도구: LocalTTS

평가용 음성을 비용 없이 만들려고, 다른 프로젝트에서도 쓸 수 있는 로컬 음성 서버를 만들었습니다.
- **기능:** OpenAI API와 같은 형식으로 TTS(일본어 18, 한국어 11, 영어 목소리)와 Whisper STT를 제공합니다. 일본어를 한국인이 읽는 한글 독음으로 바꾸는 변환기(표기 방식 선택 가능)도 들어 있습니다.
- **Python 3.14 호환 작업:** 상위 패키지 버전 불일치 우회, GPU 실행 연결(TTS 약 55배 가속)을 했습니다.

## 한계

- 질의는 모두 색인된 가사에서 만든 합성 질의이고, 음성은 TTS입니다. 사람의 실제 녹음, 노래, 콧노래는 재지 않았습니다.
- 정답 곡이 항상 DB(450곡)에 있는 닫힌 집합 평가입니다.
- 추천 품질, Spotify 연동, UI는 평가하지 않았습니다.
