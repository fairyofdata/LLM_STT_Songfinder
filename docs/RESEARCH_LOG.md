## 0. 목표와 제약

- **목표:** 「흐릿하게 기억나는 가사를 입력하거나 말했을 때 원래 곡을 찾는가」를 정량화하고, LinkedIn·포트폴리오에 쓸 근거와 차트를 만든다.
- **제약** (요청 시점에 정함, 이후 계속 지킴)
  - 가사 원문을 결과, 차트, 로그, 커밋 어디에도 새로 내보내지 않는다. 질의는 id와 인덱스로만 기록한다. ([ADR-0002](adr/0002-no-lyric-text-in-outputs.md))
  - `app.py`와 `frontend/`는 수정하지 않는다. 의심 버그도 보고만 한다. ([ADR-0004](adr/0004-report-bug-without-fixing.md))
  - OpenAI API는 비용을 먼저 추정하고, 1달러를 넘으면 묻는다.
  - 콧노래·멜로디 검색을 주장하지 않는다.
  - push는 사용자 확인 뒤에만 한다.
- **범위:** 곡 식별 단계만 다룬다. 추천 품질, Spotify, UI는 범위 밖이다.

## 1. 기본 텍스트 평가 (커밋 `f460410`)

- **설계:** [ADR-0001](adr/0001-reimplement-app-logic-and-verify.md), [ADR-0003](adr/0003-song-level-ground-truth.md)
  - `app.py`를 import하지 않고 식별 로직을 `eval/common.py`에 다시 구현했다. 표본 140개로 `app.py`와 대조해 140/140 일치를 확인했다.
  - 정답 단위는 곡이다. 가사 줄 top-2048을 곡으로 묶어 중복을 없앤 순위를 쓴다.
  - 질의는 450곡 × 줄 2개 × 5유형(원문, 앞 절반, 단어 30% 누락, 오타 10%, 인접 두 줄)이다. 시드 5개로 22,440개다.
  - 여러 곡에 똑같이 있는 줄로 만든 질의는 「모호」로 표시해 따로 집계했다.
- **결과**

  | 지표 | 값 |
  |---|---|
  | Recall@1 / @10 (모호 제외) | 60.6 ± 0.6% / 76.2% |
  | 유형별 Recall@1 | 오타 79.8%, 단어 누락 53.3%, 인접 두 줄 35.3%, 앞 절반 32.9% |
  | 판정선 0.4의 음의 대조군 오판정률 | 93.3% (DB에 없는 문장 90개 중 84개 통과) |
  | 판정선 0.8일 때 | 오판정률 7.8%, 정확도 57.6% |
  | 요약 분기 버그 | 가사 질의에서는 발동 0%. 요약문 질의에서는 현행 0.2%(곡 0~6번만 반환) vs 고친 변형 100% |

## 2. `whisper-1` 음성 경로 (커밋 `c601fbf`)

- **규모:** 처음 요청은 약 50개였다. 하지만 50개로는 95% 신뢰구간이 ±13%p라 인용하기 어렵다. 그래서 1달러 기준 안에서 1,341개(447곡 × 원문/앞 절반/단어 누락)로 늘렸다.
- **비용:** 예상 $0.636, 실제 약 $0.495. 오디오와 전사문은 저장하지 않았다.
- **결과:** 입력 62.7% → 음성 40.7%. 입력으로만 맞힌 경우 311 대 음성으로만 맞힌 경우 16이다. 원문 한 줄은 75.6%다.
- **문제 발견:** 클립의 99.6%가 5초 미만이었다. 앱 `/stt`는 5초 미만 녹음을 거부하므로, 앱이 실제로 받지 않는 입력으로 잰 것이다. 이 문제는 5절에서 해결했다.

## 3. 방법론 점검 (사용자 요청)

사용자 질문 「TTS로 STT를 평가하는 게 맞는 방법인가」에 대해 내린 결론은 다음과 같다. ([ADR-0005](adr/0005-tts-speech-as-proxy.md))
- TTS 평가는 상대 비교, 오류 원인 분해, 회귀 시험에는 타당하다. 실사용 정확도의 근거로는 쓸 수 없고, 낙관적 상한으로만 읽어야 한다.

개선 항목은 둘로 나눴고, 사용자가 둘 다 진행하도록 지시했다.

| 묶음 | 항목 |
|---|---|
| P1 | 앱 길이 질의, 곡 단위 부트스트랩·McNemar, 문절 단위 교란 재설계, 사람 맹검 검수, 가나/한자 분리 |
| P2 | 여러 목소리, 한글 독음 표기 변이, 채널 증강 |

사용자의 다른 제안도 같은 방식으로 검토했다.
- **채택:** ELECTRA·디퓨전식 단어 치환과 누락, 한국인 발음을 음차로 흉내 내기 ([ADR-0008](adr/0008-memory-error-perturbations.md), [ADR-0011](adr/0011-korean-speaker-approximation.md))
- **기각:** 「짧으면 천천히 읽히자」. 내용 양과 말 속도가 뒤섞이기 때문이다. 대신 무음 패딩으로 한 줄 조건(S)을 만들었다. ([ADR-0007](adr/0007-app-length-voice-queries.md))

## 4. LocalTTS 구축 (`C:\Users\fairy\LocalTTS`, 별도 저장소)

평가용 음성을 비용 없이 만들고 다른 프로젝트에서도 쓰려고 만들었다. ([ADR-0006](adr/0006-local-tts-stt-service.md), 세부는 LocalTTS 저장소의 `docs/adr/`)

**구성**
- OpenAI 호환 HTTP 서버(127.0.0.1:8880)와 Python API, CLI
- TTS: Kokoro(일본어 5), Supertonic-3(31개 언어 × 10목소리), Windows OneCore(일본어 3, 한국어 1)
- STT: Whisper large-v3, GPU fp16 일괄 처리(클립당 약 0.3초)
- `ja_to_hangul` 독음 변환기: 표기 변이 4축

**막힌 곳과 우회**

| 문제 | 원인 | 조치 |
|---|---|---|
| CUDA torch 설치가 멈춤 | pytorch CDN 속도 약 0.56MB/s, cu128에 3.14용 torch 2.14 없음 | cu126으로 다시 설치 (약 1시간) |
| kokoro가 `numpy==1.26.4`를 고정 | 3.14용 빌드 없음 | `--no-deps` 설치 |
| misaki 0.9.4가 3.13 미만으로 표시 | — | `--ignore-requires-python` |
| mojimoji, spacy | 3.14용 빌드 없음 | mojimoji는 jaconv 대체 모듈. spacy는 빈 대체 모듈로, 영어 Kokoro만 포기 |
| torch DLL 초기화 실패 (WinError 1114) | winrt를 먼저 불러온 뒤 torch를 불러옴 | 패키지가 torch를 먼저 불러오도록 함 |
| Kokoro 음성이 0.35초로 잘림 | misaki 0.9가 (음소, 토큰) 묶음을 반환하는데 kokoro 0.7은 문자열을 기대 | g2p와 모델을 직접 호출 |
| transformers 일괄 처리 + 언어 반환 버그 | 라이브러리 버그 | `generate`를 직접 호출하고 `detect_language`로 언어를 읽음 |
| Supertonic HTTP 400 | 어휘에 없는 드문 한자 | 그 단어를 UniDic 가나 읽기로 바꿈 |
| Supertonic HTTP 500 | 문장부호 없는 긴 글이 1,000프레임 attention 한계를 넘음 | 80자 조각으로 나눔 |
| Supertonic이 CPU에서 클립당 약 9~25초 | CPU 실행, 다른 작업과 경쟁 | onnxruntime-gpu로 0.17초. 1.31은 CUDA 13을 요구해 1.24.1로 고정 |

## 5. 앱 길이 음성 본 실험 (커밋 `411dfeb`)

- **질의:** 곡마다 연속 2~6줄, 공백 제외 55자 이상. 말소리 중앙값은 9.9초이고, 5초 미만인 5.9%는 무음을 덧붙였다.
  - 처음 설정(30자 이상)으로는 중앙값 4.4초에 3분의 2가 5초 미만이라, 시험 실행 뒤 늘렸다.
- **조건:** 5조건(A~D, S) × 음질 2 × 언어 설정 2 = 받아쓰기 8,996번. 목소리는 일본어 18개, 한국어 11개이고, 곡마다 표기 변이·속도·음높이를 바꿨다.
- **실행 사고**
  - 665번째 클립에서 HTTP 400이 났는데, 출력을 grep으로 걸러 종료 코드가 0으로 나오는 바람에 「완료」로 보였다.
    - 교훈: 파이프라인 출력은 실제 파일 수와 로그로 확인한다.
  - 클립 1개(song319-B)는 HTTP 500으로 빠졌다. 그 곡은 아래 데이터 품질 문제로 주 집계에서 뺐다.
- **결과 (깨끗한 음질, 449곡)**

  | 비교 | 결과 | 유의성 |
  |---|---|---|
  | 한국인 발음 vs 원어민 (언어 자동) | 35.6% vs 47.2%. Whisper가 한국인 발음 클립의 35%를 한국어로 감지 | p = 1×10⁻⁵ |
  | 일본어 고정 시 | 차이 사라짐 (43.2% vs 45.9%) | p = 0.32 |
  | 단, 원어민 음성에 일본어 고정 | 영어 줄을 가타카나로 받아 적어 오히려 하락 | p = 0.03 |
  | 한 줄 vs 5줄 | 76.2% vs 47.2% (입력해도 99.6% vs 67.0%). 줄 단위 색인과 여러 줄 질의가 맞지 않음 | p = 2×10⁻²¹ |
  | 열화 음질 | 원어민 47.2 → 42.5%. 한국인 발음은 35.6 → 43.7%로 오히려 상승 (잡음이 한국어 감지를 35% → 9%로 낮춤) | |
  | 교차 확인 | OpenAI TTS → `whisper-1` 한 줄 75.6% ≈ 로컬 한 줄 76.2% | |

## 6. 기억 오류 교란 곡선

- **1차 버전의 문제:** UniDic 형태소 단위로 바꿨더니 다음 문제가 생겨 폐기했다.
  - 활용 어미가 깨짐
  - 일본어 단어가 영어 단어로 바뀜
  - 영어 자리에 XLM-R이 덴마크어 단어를 넣음
- **2차 버전:** 문절 단위, 같은 문자 체계·품사·활용, 가사 DB에 있는 말만 쓰도록 했다. 7유형 × 20/40/60%다. ([ADR-0008](adr/0008-memory-error-perturbations.md))
- **시드:** 5개로 시작했지만 CPU 경쟁으로 시드당 18분 → 60분이 됐다. 이미 끝난 세 시드가 서로 거의 같아 3개로 확정했다. ([ADR-0010](adr/0010-noise-curves-three-seeds.md))
- **결과 (모든 유형이 적용되는 공통 원본 줄 1,607개, Recall@1, 20% → 60%)**

  | 유형 | 20% | 60% |
  |---|---:|---:|
  | 조사 바꾸기·빼기 | 97 | 93 |
  | 동의어 | 83 | 66 |
  | 섞기 | 78 | 35 |
  | 소리 비슷한 말 | 68 | 27 |
  | 같은 읽기 다른 표기 | 65 | 23 |
  | 문맥상 그럴듯한 말 | 64 | 24 |
  | 어절 빼기 | 69 | 15 |

  해석: 의미 임베딩이라 뜻에는 강하고 소리·표기에는 약하다.
- **사람 맹검 검수:** 시트 100행을 레포 밖에 만들었다. 판정은 아직이다.

## 10. 교훈

1. **평가 대상과 앱 입력을 먼저 맞춘다.** 1~2초 한 줄 음성은 앱이 받지 않는 입력이었다. 앱 코드의 제약(5초)을 평가 설계 전에 확인했어야 했다.
2. **같은 데이터로 고른 값은 따로 떼어 둔 데이터로 확인한다.** 투표 가중치가 그랬다.
3. **장시간 작업은 실패를 숨기지 않게 짠다.** 파이프와 grep은 종료 코드를 가린다. 클립 단위로 실패를 기록하고 이어서 할 수 있게 캐시를 둔다.
4. **느릴 때는 먼저 잰다.** CPU 경쟁과 실행 장치(CPU/GPU)를 확인하고 나서야 55배 개선을 찾았다.
5. **사용자 제안도 방법론으로 검토한다.** 받아들일 것과 바꿀 것을 근거와 함께 말한다.
